Beyond stat_grid/panel/list/suggestions, thirteen more component types exist — reach for whichever actually fits the shape of the request, don't default to 'list' out of habit:
- 'metric': when the real answer is exactly ONE number (e.g. "how many are blocked/unread/open right now?") — a single big emphasized figure reads far better than a one-card stat_grid or a list of one row. Put exactly one entry in 'stats', a real count of what you actually fetched.
- 'timeline': for requests that are naturally about recency/order over a SET of records — "what's changed recently", "what came in this week", "newest first". Sort the real records by their real date/timestamp and put them in 'rows' in that order (name = the record's identifying text, note = the real date, e.g. "Updated 2026-08-30"). Never invent a fake history for a single record when there's no real per-record history available — timeline here means several real records in real chronological order, nothing else.
- 'chart': when a request is about how records split up/compare across categories — "break down by status", "how are these distributed by priority/sender/channel". Put one 'stats' entry per category (label = the category; value = the real count in it as a plain number string, e.g. '4') — never a stat_grid for this shape of request, a chart's bars make the comparison visible in a way separate cards don't.
- 'alert': when the real answer IS a single urgent condition worth calling out on its own — "is anything overdue", "anything I should know about right now". Set 'title' to the real, derived claim, 'badge' tone to 'critical'/'warning' to match its urgency, and 'subtitle' to one more sentence of real context if useful. Only use this when there's one real, specific thing worth flagging — if the honest answer is "nothing urgent right now," use 'empty_state' instead (below), never a fabricated or forced alert.
- 'task_queue': when a request is about outstanding work/to-dos rather than a general list — "what's overdue", "what still needs a reply". Same row shape as 'list', rendered as a checklist instead — use it when the request frames things as work to get done, use plain 'list' when it's just asking what exists.
- 'data_table': when a request needs several real fields compared side by side across multiple records — use real columns (2-5 of them) instead of cramming extra facts into a list row's one 'note' string. Each table_rows entry's 'values' must have one real value per column, same order. This is often a better fit than 'list' specifically when the request names more than two fields it cares about.
- 'detail_view': when the ENTIRE request is about one specific record and that record IS the whole answer — e.g. "show me ENG-470", "tell me about this ticket." Same title/subtitle/badge/fields/action shape as 'panel', just a bigger, more prominent treatment for a genuine single-record deep-dive. Use 'panel' instead when the detail box is a supporting piece of a bigger screen, or for a handful of aggregate stats.
- 'status_badge': a quiet, single-line status indicator — e.g. "Sync status: Up to date", "Inbox: 3 unread." Set 'title' to the short label and 'badge' to the real status (text + tone) — the badge here IS the claim, not decoration, so it must be as real/grounded as an alert's title. Use this instead of 'alert' when the condition is routine information, not something urgent enough to warrant a loud banner.
- 'empty_state': the honest, explicit way to say "nothing matched, and that's the real answer" — e.g. "No blocked issues right now," "Nothing overdue." This is the CORRECT component for a genuine zero-result finding — never state a "nothing found" claim only in plain chat text (see render_dont_narrate.md); render it here instead, even when it's the only component on the screen.
- 'error_state': a structured, visible card for "this data source failed" as part of the rendered screen itself — e.g. when one connected app's real fetch call errored (an expired token, a real upstream problem) but another relevant, connected app's data IS available. Set 'title' to what failed, 'subtitle' to why or what to do, 'action' to a real recovery step if there is one (e.g. "Reconnect Gmail"), and still render the OTHER app's real data alongside it — never let one source's failure block a screen that has other real, usable data to show.
- 'connection_state': when a request is literally about integration/connectivity status — "what's connected right now", "which apps need reconnecting". Put one 'stats' entry per app (label = app name, value = its real state as a short string like "Connected"/"Not connected"/"Token expired", tone = good/critical to match). Use this instead of 'stat_grid' — a connectivity state is a short status string, not a number to emphasize.
- 'pagination': a real-data status line for "page X of Y, Z total" — only use this when you actually have real page/total numbers from what you fetched; never invent or estimate them. Most current fetch tools return everything in one call with no real paging, so this will rarely apply yet.
- 'popover': a click-to-reveal disclosure for extra detail that would clutter the main view if always shown — set 'title' to the short trigger label (e.g. "Show full details") and 'fields' to the real key/value content revealed underneath. Good for a secondary handful of real fields on an otherwise-focused screen.
- Tooltip text: 'fields' entries and any 'badge' object can carry an OPTIONAL 'hint' — a short explanatory string shown on hover (e.g. a field's hint might read "Story points = relative complexity estimate, not hours"). A hint EXPLAINS what something means; it must never be used to sneak in a new fact or number that isn't already stated elsewhere on the real, grounded parts of the screen.
